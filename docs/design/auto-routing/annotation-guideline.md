# 深度档标注手册

给标注员用。读完这份就能开始标，遇到拿不准的往下翻「难例」。

---

## 1. 你在标什么

你会看到一条文本：**某个人给 AI coding agent 新建任务时写下的第一句话**。可能来自聊天窗口，可能是一条 GitHub issue，可能是一句口语。它是这个人说的第一句，AI 还没有回应过。

你要给它打一个档：**swift** / **standard** / **deep**。

这个档位决定 rove 给这个任务分配多强的模型。打高了浪费钱，打低了活干不好。

---

## 2. 唯一的判据

> **这个人把「怎么做」说了多少？剩下多少要 AI 自己想？**

只看这一件事。

三档就是这一个量的三段：

| 档 | 这个人给到哪一步 | AI 还得自己想什么 |
|---|---|---|
| **swift** | 说了怎么做 | 不用想，照做 |
| **standard** | 说了要什么，没说怎么做 | 得自己找改哪、怎么改 |
| **deep** | 连要什么都没说清 | 得先想明白目标是什么 |

---

## 3. 不要看的东西

这几条是最容易把人带偏的。标的时候主动提醒自己一遍：

- **不看工作量。** 一个改动要干三天、要碰十个文件，和它是什么档没关系。「把这个按钮挪到右边」哪怕要改十处，只要说清了怎么改，就是 swift。
- **不看难度。** 修起来难 ≠ 想起来难。一个 bug 可能极难修，但如果这个人已经指出了原因和改法，AI 不需要自己想，还是 swift。
- **不看文本长短。** 长的 issue 经常是 standard（一堆环境信息和复现步骤，但没说怎么修），短的一句话经常是 swift（「把 X 改名成 Y」）。
- **不看语言。** 中文英文中英混杂一视同仁。
- **不看这个人写得糙不糙。** 错字、没标点、口头禅都不影响判断。
- **不看三档的比例。** 一批标下来七成是 standard 就是七成，不要为了凑均匀去改。

---

## 4. 标注流程

按顺序问自己两个问题。**先问第二个，再问第一个**——先把 deep 摘出来，剩下的再分 swift / standard。

```
        ┌─ 这个人说清楚了「要做成什么样」吗？
        │
        ├─ 没有 ─────────────────────────────→  deep
        │
        └─ 说清楚了
             │
             └─ 他还说了「改哪、怎么改」吗？
                  │
                  ├─ 说了 ──────────────────→  swift
                  │
                  └─ 没说 ──────────────────→  standard
```

---

## 5. 三个档的定义和例子

### swift —— 怎么做已经在文本里了

**判据**：AI 不需要做任何选择。换一个人来做，做出来的东西是一样的。

满足下面任一条就是 swift：

- **指到了具体位置和改法**：「config.yml 里加个 `spawn-protection-radius`，默认 16，超了不让放方块，op 除外」
- **这个人已经自己查过了**：「profile 了一下是每次移动都在同步 read_dir，加个几百毫秒缓存」——原因找到了，剩下是照做
- **说了照谁的做法**：「参考 vuetify 同名 prop 的行为」「像 fzf 那种 ctrl+r」
- **一个具体到打开就能看见的现象**，没有条件、没有猜测：「深色模式下代码块背景和正文一个颜色」
- **纯操作**：「pull 最新代码看看合了什么」「把 X 改名成 Y」「用这个 skill 跑一遍」
- **改一处文案 / 链接 / 样式**

**真实例子**

> `pull最新代码 检查最新合入 是啥`
> → **swift**。一条命令的事，没有任何需要判断的地方。

> `quill transcirbe没办法打断但是 mic很容易误触 就导致经常不小心录制一秒导致之前的transcrbe被打断`
> → **swift**。行为描述死了，复现一次就知道改哪。标注时写的理由是「需求明确、有用户行为、复现就好」。

> `https://github.com/CodeFox-Repo/wisp/pull/276/changes 先检查这个 看看有没有问题 我觉得cmt太长了 处理下吧`
> → **swift**。给了具体的 PR 链接和具体的意见（commit message 太长），照做即可。

> `[FR] take if syntax is not mapped -> take one by symlink's target` + 两行 shell 复现
> → **swift**。两行命令把现状和期望都摆出来了，改法直接读得出来。

---

### standard —— 要什么说清了，怎么做没说

**判据**：目标明确，但 AI 得先去看现有代码是怎么写的，才知道改在哪一层、要不要动别处。

满足下面任一条就是 standard：

- **一个明确的 feature 请求**，没说怎么实现：「能不能支持导出 json，现在只有 csv」
- **点名了具体的东西（flag / 文件 / 接口 / 平台），说了要变成什么样，但没说怎么改**——这是最容易误判成 swift 的一类，见下面难例
- **症状 + 这个人自己猜了个原因（但没验证）**：「重复回复同一条消息，是不是没加去重」——猜的原因就是目标，AI 去验证它
- **给了参考说「照这个做」**：「复刻 omp.sh 的主页」
- **规整的 bug 报告**：标题、版本号、环境、复现步骤、贴了报错或代码——**但对该改哪里只字未提**

**真实例子**

> `增加一个 在filepane 按a就是at 一个relative 路径吧 目录和文件都可以我理解`
> → **standard**。说了键位和效果，但「插到哪、补全怎么做、相对于谁」都没定。

> `修复一个bug file tab永远只开一个有感觉吗 不需要多个`
> → **standard**。知道要多开 tab，但得先去看现在为什么只开一个。

> `Deprecate --style=auto in favour of --decorations=auto`（附一段理由）
> → **standard**。点名了两个 flag、说了要废弃哪个，但废弃提示放哪、老配置怎么迁移、文档改哪些，一句没说。

> `[Feature]透视表可以增加表头排序功能吗` + 版本号 + 需求描述
> → **standard**。目标非常清楚（按列排序），实现完全没提。

> `复刻 https://omp.sh/ 主页 for rove这个产品`
> → **standard**。目标给死了（那个页面长什么样），但得自己看现有结构怎么接。

---

### deep —— 目标本身要 AI 去找

**判据**：动手之前得先想清楚「做成什么样才算做完」。

满足下面任一条就是 deep：

- **开放式**：「有什么可以优化的」「什么方向值得做」「换架构有必要吗」
- **让人去调查**：「调查一下审计日志表为什么涨这么快」「瓶颈在哪」
- **只问可不可以，没说要做**：「有没有办法让传送冷却按权限组不一样」——先要判断方案可不可行
- **模糊症状，带条件、不稳定复现、而且这个人没给任何猜测**：「有时候会跑到屏幕外，多屏的时候」「感觉卡一下」
- **一个设计问题**：「rove 回复是插入 prompt 再 enter，但用户正在输入的时候怎么办呢」——没有既定答案，要先想清楚该怎样

**真实例子**

> `你认为有啥ui可以优化的地方吗`
> → **deep**。没有终点，AI 得先定义什么算「优化」。

> `这个仓库还有什么值得做的优化` / `整个仓库现在有什么方向值得探索和完善的`
> → **deep**。标注时写的理由是「探索性质，依赖高级模型」。

> `你检查一下现在wisp线上版本的memory 感觉有点太多太杂了。。 根本搜不到有用信息 和claudecode的memory实现完全不一样`
> → **deep**。「太多太杂」不是一个可执行的目标，得先搞清楚问题到底是什么。

> `有一个branchmerge了什么导致 rove 最新分支直接挂了 我本地挂了 crash pane打不开了`
> → **deep**。只有症状，没有猜测，不知道是哪次合并、哪个模块。

> `话说我们之后能做到资源包的加载不用重启游戏能做到吗`
> → **deep**。在问可行性，不是在下需求。

## 6. 难例：容易搞错的边界

### 6.1 点名了具体符号 ≠ 说了怎么做

这是最大的一类错。看到 `--style=auto`、文件名、riscv64 这种具体符号，很容易判成 swift。**要分清这个符号是「要改的东西」还是「改的方法」。**

| 文本 | 档 | 为什么 |
|---|---|---|
| 「config.yml 里加个 `spawn-protection-radius`，默认 16，超了不让放方块」 | **swift** | 符号 + 取值 + 行为，改法完整 |
| 「废弃 `--style=auto`，改用 `--decorations=auto`」 | **standard** | 只说了要改哪个符号，怎么改一句没提 |
| 「给 binary 加 `riscv64gc-unknown-linux-gnu` 和 musl 两个 target，现在 CI 在这两个上是红的」 | **standard** | 点名了目标平台，但为什么红、怎么修没说 |

**自检**：读完之后，「第一步打开哪个文件、改哪一行」你说得出来吗？说得出来是 swift，说不出来是 standard。

### 6.2 贴了复现脚本 ≠ 说了怎么修

长 issue 里的代码块、版本号、环境信息，那些是**背景**，是帮人复现的，不是改法。

> ``` `--color nth:` won't respects `current-fg (fg+)` when FZF_DEFAULT_OPTS has `--color nth:attr` ``` + 20 行 bash 复现脚本 + 版本号
> → **standard**。脚本是用来复现的，它没告诉你颜色解析那段代码要怎么改。

### 6.3 有猜测 vs 没猜测，分开 standard 和 deep

同样是症状描述，看这个人有没有给出一个**可以去验证的猜测**：

| 文本 | 档 |
|---|---|
| 「paste 多行文本好像丢字符，**是不是 truncate 了**」 | **standard**（猜测就是目标，去验证它） |
| 「有一个 branch merge 了什么导致最新分支直接挂了」 | **deep**（只有症状，无从下手） |

### 6.4 具体到打开就能看见 vs 带条件、不稳定

| 文本 | 档 |
|---|---|
| 「深色模式下代码块背景和正文一个颜色」 | **swift**（打开就看见，一句话说死） |
| 「弹出面板**有时候**会跑到屏幕外面，**多屏情况下**」 | **deep**（先要找到触发条件） |

### 6.5 「能不能做 X」——看 X 说清没有

| 文本 | 档 |
|---|---|
| 「能不能支持导出 json，现在只有 csv」 | **standard**（X 很明确，就是 json 导出） |
| 「能不能做到资源包加载不用重启」 | **deep**（在问可行性，方案本身要先判断） |

区别在于：前者是「请做这个」，后者是「这个做得到吗」。

---

## 7. 不算任务的（标 drop）

- 只有一行报错，没说要做什么
- 纯闲聊、问候
- 只有一个链接或一张图，没有任何文字说明
- 明显是测试消息（「回复 ok」「1 到 100 数一遍」）

drop 不是一个档位，是「这条不进数据集」。**不要为了凑数把它硬塞进三档里。**

---

## 8. 拿不准的时候

**不要猜了就过。** 标一个「不确定」，并在备注里写一句「卡在哪两档之间、为什么」。

这些条目会送去仲裁，而且是这份手册下一版要改的地方——你写的那句话比那个标签有用得多。

**已知的一条不一致**（提前告诉你，免得你困惑）：早期有一条被标成 deep 的理由是「需求太大，需要狠狠思考」——那是按工作量判的，和第 3 节「不看工作量」冲突。这条标签保留未改，但**你不要照着它来**。按工作量判会让整份数据自相矛盾。

---

## 9. 实操

- **一次标 30–50 条就休息。** 连着标一两百条之后，边界会开始漂。
- **不要看别人的标注再标。** 双标的价值全在两个人独立。
- **不要回头改前面的。** 手感变了就是变了，回头改会把前后搅在一起；有系统性的改动想法，写进备注，仲裁时统一处理。
- **备注里写「为什么不是隔壁那档」**，比写「为什么是这档」有用。

---

## 10. 一句话总结

> 你判的不是这活有多难、多大，而是**这个人替 AI 想了多少**。
> 想完了 = swift，想了一半 = standard，还没开始想 = deep。
