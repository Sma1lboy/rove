How a change becomes a release

Changeset.changeset/*.mdWritten with the PR

Every build passes the same test gates between the tag and the publish.

Each change brings its own release note. The pull request adds a Markdown file under .changeset/. Merging consumes those files, writes the new version and appends their text to CHANGELOG.md.

The tag is pushed from main, the publish happens in CI, and the GitHub release body is that changelog entry verbatim, so this list is fetched, not written.

Two channels

latestThe stable line: batched, reviewed releases. This is what a plain install gives you, and what the list above shows.
nightlyAn automated daily cut from main. Same test gates, but its contents have not been reviewed as a set.

You do not configure a channel. The build you are running is the channel. Update checks follow whichever one you installed from, and rove update with no arguments never moves you between them.

rove update list browses recent versions and rove update dry-run prints the command without running it. Updates go through whichever package manager owns the rove on your PATH, so a new version cannot land in a shadowed prefix.
