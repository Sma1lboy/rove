Close the macOS FSEvents startup-drop window in the daemon's shared file-watch trigger (issue #61, same bug class as the plugin-registry fix). `file-watch-trigger.ts` — backing the ui-prefs, keybindings, and pty-exit fan-outs — previously rode chokidar with a one-shot `ready` reconciliation, which narrowed but did not close the window where FSEvents arms asynchronously: a probe still measured ~3% permanent single-write loss for writes landing near `ready` under load. It now stat-polls the watched basenames (mtimeNs + size + inode every 200ms), with the baseline stamp taken synchronously before the caller's first load, so no write can fall between the two; the ui-prefs and pty-exit watchers were reordered to load after the watch starts. Worst prior consequence: an engine crash record written during daemon startup could lose its `session.exited` plugin event forever. This also drops the chokidar dependency. The filetree pane's recursive worktree watch keeps fs.watch deliberately — stat-polling a whole tree is disproportionate when a missed event only means a stale pane until the next change or a manual `r` — and now documents that trade-off.
